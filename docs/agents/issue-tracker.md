# Issue tracker: GitHub intake and local planning

GitHub issues are authoritative for incoming requests and their global completion. Local Markdown is authoritative for an effort's decisions, specification, and implementation tickets. Fetch or import on demand; there is no background or bidirectional synchronization.

## Routing

- GitHub URLs and bare `#<number>` references identify GitHub issues in `Submoon/ttrpg-cluster-control`. Local tickets are identified by file path, never by a bare GitHub-style number.
- For a small request, read the GitHub issue, use `/triage` if clarification is needed, then `/implement` in the same session. An already agent-ready request can go straight to `/implement`; a local copy is unnecessary.
- For an understood multi-session effort, clarify with `/grill-with-docs` as needed, then use `/to-spec` and `/to-tickets` locally.
- For a large, unclear effort, use `/wayfinder` locally, then `/to-spec` and `/to-tickets` once decisions make the work buildable.
- Tickets produced by `/to-tickets` are already agent-ready; implement them blockers-first rather than triaging them again.

## GitHub operations

Use `gh` from PowerShell. To fetch a request, read its body, comments, labels, state, and URL:

`gh issue view <number> --repo Submoon/ttrpg-cluster-control --json number,title,body,labels,comments,state,url`

Triage comments and labels for a named GitHub request belong on that GitHub issue. Use `--body-file` for multiline comment bodies. Remote writes require the user's direction or approval; importing a request does not change its labels or state.

**PRs as a request surface: no.**

## On-demand local import

1. Fetch the GitHub issue before planning. If it fits one implementation session, keep working from GitHub without creating a local effort.
2. Otherwise, create `.scratch/<feature>/`. Add a `## Source issue` section to its map or specification with the issue title linked to its full GitHub URL, the fetch date, scope, acceptance criteria, and relevant comments or unresolved questions.
3. Link local tickets to the source map or specification, and include the requirements each ticket needs to stand alone. Local files are planning artifacts, not a second independently edited copy of the GitHub issue.
4. Re-fetch the source when resuming an imported effort and before reporting completion. Surface scope conflicts for a decision rather than overwriting local decisions or silently following a stale snapshot.

## Local structure

- Store each effort under `.scratch/<feature>/`.
- Use `map.md` for a Wayfinder map, `spec.md` for a specification, and `tickets/<NN>-<slug>.md` for individual decision or implementation tickets. Preserve existing ticket paths.
- Give each map and ticket a human-readable title. Use relative Markdown links whose link text is the ticket title.
- Put `title` and `status` in YAML frontmatter; tickets also have `label`, `type`, a parent-map or specification link, and optional `assignee`. Use `label` only for the `wayfinder:<type>` value. Triage roles are separate; see `docs/agents/triage-labels.md`.
- Append local triage notes and agent briefs under `## Comments`; start each with `> *This was generated by AI during triage.*`.
- When a planning skill says to publish a specification, map, or implementation ticket to the tracker, write the corresponding local file. When triage targets a GitHub issue, publish its brief or notes on that issue instead.

## Local ticket lifecycle

Use these exact `status` values:

- `open` — new, unclaimed, or available for work. This is the initial status.
- `in-progress` — claimed and actively being worked.
- `blocked` — waiting on a dependency or outside decision. Record the blocker; return to `open` when it clears unless work resumes immediately.
- `closed` — resolved or ruled out of scope. Record the outcome in `## Resolution`.

An open ticket without an assignee is unclaimed. Add an assignee and set `status: in-progress` before working it. A blocked ticket is not on the frontier.

The Task Board maps `open` to planned, `in-progress` to in progress, `blocked` to blocked, and `closed` to done. Keep triage roles out of `status`.

## Wayfinding operations

- Keep the map as an index: closed decisions go in `Decisions so far`; do not list open tickets there.
- Record dependencies in `## Blocked by`, with links to blocking ticket titles. A ticket is available only when all blockers are resolved and it is unclaimed.
- Record a resolved ticket's answer in `## Resolution`, set `status: closed`, and add a concise linked gist to the map's `Decisions so far`.
- Link research/prototype artifacts from the relevant ticket rather than pasting large artifacts into the map.
- Close the map when its destination is reached; a closed decision map does not mean the product request is implemented.

## GitHub completion

Closing a local ticket or map never automatically closes the GitHub source. Report progress or close the source only when requested; close it only after all of its acceptance criteria are satisfied. Summarize the outcome and reference the local effort and relevant PR when available.
