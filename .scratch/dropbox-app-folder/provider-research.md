# Dropbox App Folder privacy

Reviewed on 2026-11-16 for [Back up and restore a Jump Cluster with Dropbox](https://github.com/Submoon/ttrpg-cluster-control/issues/55). This note records public Dropbox documentation and historical answers from Dropbox staff. No live Dropbox account, app registration, token, or API response was used in this research.

## App Folder and membership

- Dropbox App Folder is a content boundary configured during app registration. OAuth scopes separately authorize actions. File paths supplied by the app are relative to its dedicated folder, conventionally displayed as `/Apps/<app folder name>` in the English Dropbox UI. For example, use `/probe/fixture.json` with the API and `path: ""` to list the app folder contents. `files/get_metadata` explicitly excludes the API root. That leaves a gap when trying to query the app folder itself. Dropbox staff say App Folder requests are already rooted and reject `Dropbox-API-Path-Root`. The generic header documentation describes broader namespace routing for supported requests. [OAuth content access](https://docs.dropboxapi.com/dropbox-api/docs/oauth#content-access) · [App-relative paths](https://community.dropbox.com/en/discussion/807557/api-error-path-not-found-when-creating-shared-link) · [Root listing](https://community.dropbox.com/en/discussion/275864/path-not-found-error) · [Get Metadata](https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/files/get-metadata) · [App Folder path-root restriction](https://community.dropbox.com/en/discussion/769690/400-error-path-root-is-not-supported-for-sandbox-app)
- Dropbox's API specification defaults `allow_app_folder_app` to false. `sharing/list_folder_members`, `sharing/list_file_members`, their continuations, and the shared-folder and shared-file metadata routes omit the App Folder opt-in. With access to the file-members route, `include_inherited` defaults to true and reports members whose access comes from a parent shared folder as well as direct members. The batch route omits inherited users and groups. A restricted token lacks these membership and sharing-metadata lookups even with `sharing.read`. [Route attributes](https://github.com/dropbox/dropbox-api-spec/blob/main/stone_cfg.stone) · [Sharing routes and input types](https://github.com/dropbox/dropbox-api-spec/blob/main/sharing.stone) · [Sharing guide](https://docs.dropboxapi.com/dropbox-api/docs/sharing#reading-file-membership)
- The `sharing/share_folder` error schema explicitly rejects member-sharing the app folder and folders inside it with `is_app_folder` and `inside_app_folder`. Dropbox staff also say App Folders are incompatible with placement inside member-shared folders, team folders, and team spaces. These are reasons to attempt the fixture configurations in the Dropbox UI and record whether Dropbox prevents them. A restriction on creating member-shared folders and a restriction on using membership routes do not resolve direct invitations to individual files. `sharing/add_file_member` is unavailable to an App Folder token. Whether the Dropbox UI allows a direct file invitation or a previously shared file retains any access after a move into the app folder remains an open test case. [Sharing spec](https://github.com/dropbox/dropbox-api-spec/blob/main/sharing.stone) · [Dropbox staff on App Folder placement](https://community.dropbox.com/en/discussion/461321/app-folder-in-business-root) · [Direct file sharing](https://docs.dropboxapi.com/dropbox-api/docs/sharing#shared-files)
- For an addressable folder, `files/get_metadata` and `files/list_folder` can signal shared-folder membership through `FolderMetadata.sharing_info.shared_folder_id` (a shared folder mount) or `parent_shared_folder_id` (a shared parent). `read_only`, `traverse_only` and `no_access` describe limitations on the caller. For a file, `FileMetadata.sharing_info.parent_shared_folder_id` signals a shared parent. Request `include_has_explicit_shared_members: true` to obtain the separate `has_explicit_shared_members` file flag. A true value reports explicit members, including on files outside shared folders. A missing value is indeterminate. A false value answers only the explicit-file-members question. A new file has no file metadata before creation, so the file flag cannot establish that its parent is safe before upload. Validate that each attainable sharing state changes the expected metadata under the exact restricted token. [File metadata schema and route support](https://github.com/dropbox/dropbox-api-spec/blob/main/files.stone) · [Get Metadata](https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/files/get-metadata)

## Shared link coverage

- `sharing/list_shared_links` explicitly supports App Folder with `sharing.read`. The documented targeted query accepts a nonempty `path` value, including ordinary paths and supported `id:`, `rev:`, and `ns:` references. Use `direct_only: false` to include applicable direct links and parent-folder links. Querying a folder does not enumerate the separate links to its children. File or namespace identifiers identify resources within the authorization boundary. Their accepted syntax does not establish access outside it or establish that an App Folder root ID can be discovered and queried with the scoped token. [List Shared Links](https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/sharing/list-shared-links) · [Sharing spec](https://github.com/dropbox/dropbox-api-spec/blob/main/sharing.stone) · [Sharing guide](https://docs.dropboxapi.com/dropbox-api/docs/sharing#reading-shared-links)
- The documented cursor is returned only for a request with no path. That request inventories links for the authenticated user and can be paged while `has_more` is true. Dropbox staff describe the App Folder inventory as restricted to items accessible to that app. They also document a historical case where `/scl/fi` links required a targeted path or ID lookup. Empty or exhausted inventory therefore provides no substitute for a targeted check. Treat any `has_more` response without an actionable cursor, cursor reset that leaves the scan incomplete, lookup error, or denied request as indeterminate. The spec models link `id` and `path_lower` as optional. Dropbox explicitly limits `path_lower` to items in the calling user's Dropbox where that user owns the link. [List Shared Links](https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/sharing/list-shared-links) · [Sharing spec](https://github.com/dropbox/dropbox-api-spec/blob/main/sharing.stone) · [Restricted inventory](https://community.dropbox.com/en/discussion/171268/shared-app-directory-exists-but-inaccessible-to-my-app/p1) · [Targeted modern links](https://community.dropbox.com/t5/Dropbox-API-Support-Feedback/Not-able-to-List-shared-links-having-edit-access-without-file-id/m-p/546402)
- Dropbox documents caller-specific link visibility, with links to ordinary files typically created per user. Its exhaustive team procedure enumerates links separately for each team member through `Dropbox-API-Select-User`. An App Folder user token cannot use that procedure. If another user can obtain access and produce a working link, the Warden's link results alone cannot establish complete visibility. Dropbox Help also says an externally usable view-only link may leave the Web UI showing “Only you.” Confirm fixture access with the intended recipient or a signed-out profile when the link mode allows it. [Detecting shared links](https://docs.dropboxapi.com/dropbox-api/docs/sharing#detecting-shared-links) · [Caller visibility](https://community.dropbox.com/en/discussion/677953/get-all-shared-links-for-a-file) · [Dropbox Help on link access](https://help.dropbox.com/share/share-outside-dropbox)
- App Folder is compatible with shared links. The creation route opts in to restricted apps with `sharing.write`, and Dropbox staff describe app-folder sharing through read-only links. A separate staff answer says the restricted API cannot create a link targeting its own root, though it can create a link to an addressable subfolder. Test link creation at the app folder root and its physical parent in Dropbox UI separately. No reviewed API contract establishes that targeting a child returns every applicable link to the App Folder root, the physical `Apps` container, or another ancestor outside the sandbox. The generic upward traversal description does not specify the App Folder boundary. If external access works through any such link, the restricted preflight must expose it before any backup write. [Sharing spec](https://github.com/dropbox/dropbox-api-spec/blob/main/sharing.stone) · [Dropbox staff on App Folder links](https://community.dropbox.com/en/discussion/comment/412309) · [Dropbox staff on API root links](https://community.dropbox.com/en/discussion/217441/sharing-an-app-folder)

## Dropbox Developer Console and authorization

Create a **Scoped access** app with **App folder** access. The accompanying privacy probe uses `files.metadata.read`, `sharing.read`, and `files.content.write`. The table also covers `files.content.read` for a separate download check. Use the same app and grant for all calls in each qualification run. [Dropbox Developer Console](https://www.dropbox.com/developers/apps) · [Dropbox OAuth app setup](https://docs.dropboxapi.com/dropbox-api/docs/oauth#setting-up-your-app)

| Scope | Calls exercised |
| --- | --- |
| `files.metadata.read` | List folders and continuation pages. Read fixture metadata and request the explicit-file-members flag. [Files spec](https://github.com/dropbox/dropbox-api-spec/blob/main/files.stone) |
| `sharing.read` | List shared links by target, including parent links. [List Shared Links](https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/sharing/list-shared-links) |
| `files.content.write` | Upload a new synthetic JSON file. Also covers `files/create_folder_v2` if creating a child fixture via API. [Upload](https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/files/upload) · [Files spec](https://github.com/dropbox/dropbox-api-spec/blob/main/files.stone) |
| `files.content.read` | Download uploaded bytes via the ordinary authenticated content route. [Download](https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/files/download) |

If the integration enforces a supported account type, `users/get_current_account` is an App Folder route that needs the additional `account_info.read` scope. The auth URL can request `require_role=personal` or `work`, but Dropbox says to verify account type after authorization because the URL parameter can be modified. Use Dropbox's UI for fixture sharing so the restricted app grant only reads sharing state. [Users spec](https://github.com/dropbox/dropbox-api-spec/blob/main/users.stone) · [Authorization parameters](https://docs.dropboxapi.com/dropbox-api/docs/get-started/authorization)

For API qualification on the app creator's test account, **Settings → OAuth 2 → Generate access token** provides a short-lived token usable directly in API requests. This tests the scoped provider surface before a callback is implemented. Browser qualification then uses the public app key, exact registered redirect URI, authorization code with PKCE S256, verified OAuth state, and the token exchange with `client_id` and `code_verifier`. `token_access_type=online` returns a short-lived access token. Use the authorization reference for the exchange parameters. The OAuth guide's PKCE sentence about replacing `client_id` conflicts with the reference and official SDK, which both include `client_id` and omit `client_secret` for PKCE. Use distinct browser profiles for the subsequent save and restore and confirm the browser's content requests succeed from the actual application origin. [Generated token](https://docs.dropboxapi.com/dropbox-api/docs/oauth#testing-with-a-generated-token) · [Authorization reference](https://docs.dropboxapi.com/dropbox-api/docs/get-started/authorization) · [Official JavaScript SDK](https://github.com/dropbox/dropbox-sdk-js/blob/main/src/auth.js) · [Browser requests](https://docs.dropboxapi.com/dropbox-api/docs/technical-reference/request-response-formats)

## Evidence required to qualify the destination

1. Use a disposable App Folder registration, a synthetic JSON fixture, the owner, and a second Dropbox identity or signed-out profile as appropriate. Establish the private control, then try direct member sharing of the root and child folder, placing the app folder under a member-shared parent, moving in a member-shared folder, direct file sharing and moving in a previously shared file. For each case record the exact UI outcome and externally verified access where Dropbox permits the setup. Exercise supported account types separately.
2. Independently test a direct file link, a child folder link inherited by its fixture, a link to the App Folder root, and a link to the physical parent above that root if the UI permits it. Check an already-linked parent against a synthetic file created after the link. Where a second user can create a working link, repeat the restricted owner-token lookup for that case. Compare targeted calls by app-relative path and available ID with the no-path inventory as a diagnostic. Capture redacted statuses, relevant flags, link types, and pagination state. Treat UI prevention as a fixture result and an API request error as indeterminate.
3. A non-root destination checked before transfer can address the root metadata problem only if its restricted probes detect or conclusively rule out exposure from every relevant ancestor. For sensitive backups require positive coverage of each sharing mechanism, including caller and namespace limits. A fixture reachable by a second identity while its preflight looks private disproves the proposed check. Preflight and the documented upload are separate operations and the upload exposes no ACL or shared-link precondition, so an accepted result describes the time of check. [Issue acceptance criteria](https://github.com/Submoon/ttrpg-cluster-control/issues/55) · [Upload request](https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/files/upload)

The documentation supports testing direct browser transfer with App Folder. It leaves effective link visibility for the restricted root, ancestors outside it, and links made by other users unresolved. Keep privacy qualification pending until live evidence covers those cases for the proposed destination and account types. If an applicable case remains indeterminate, return the result to the issue's destination and authorization decision.
