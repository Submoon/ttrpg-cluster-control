## Question

What theme preference, visual states, and export palette policy ensure a coherent, legible UI/map without losing edits or changing the workspace when the user switches modes or exports?

## Factual context

[Revamp the interface](https://github.com/Submoon/ttrpg-cluster-control/issues/3), reviewed on 2026-10-13, requires an explicit, remembered light/dark control, CSS tokens, and legibility across UI/maps/exports. The source presents OS default and light export for printing as considerations; their human-confirmed policy is recorded in the Resolution below. [Accessibility contrast and remove unnecessary footer](https://github.com/Submoon/ttrpg-cluster-control/issues/23) requests a WCAG AA/color-blindness audit in both modes and removal of the footer or a useful purpose for it; that realization and audit remain separate.

`main.css:3` forces dark mode and has UI/map tokens; panels retain several literal RGBA backgrounds. `map-image-export.ts:92` inlines active styles and removes handles, without a separate palette projection or explicit cleanup of selection classes. The footer (`pages/index.vue:212`) carries useful save feedback. See [the analysis](../analysis.md), themes and exports. No ratio or conformance has been measured.

## Initial proposal

An explicit local control, OS preference only when no choice exists, palettes through tokens, and a light export option for printing independent of the UI preference. Selection/focus cleanup and full-scene preservation were proposed for discussion. The human answers and authoritative Resolution below supersede this initial proposal.

## Resolution criteria

- Specify the default and persistence of the preference, independence from domain data, and absence of destructive remounts.
- Define UI/map/dialog palettes and hover/focus/selected/saving/error states, with cues beyond color.
- Choose active/light/other export palette, whether selection is exported, equivalent PNG/SVG behavior, and a readable system title.
- Set contrast/focus verification targets and the boundary with the separate audit; decide where save feedback goes if the footer is removed.
- Leave fine visual questions to the prototype; make no conformance claim without evidence.

## Blocked by

None: theme/export policies can be decided without a UI library or exact layout. Apply `grilling` and `domain-modeling`.

## Resolution

Resolved on 2026-10-13 through the human's explicit acceptance of Q1–Q5. This is the revamp's theme, accessibility-target, and image-export contract, not an implementation or completed accessibility audit. The [navigation contract](01-map-navigation-boundary.md), [interaction contract](03-touch-keyboard-interactions.md), and [state-preservation contract](05-editor-state-and-preservation.md) remain binding.

### Preference and live palette

- Provide an explicit, keyboard/touch-accessible light/dark control with a readable name and current state. Until the first explicit choice, derive the active theme from the OS; an explicit saved choice then remains stable despite OS changes.
- Remember the explicit choice durably in this browser on this device, across reloads, browser sessions, and workspaces. It is independent of domain data, workspace JSON, import/export, and cross-device synchronization. UI and both map views share the active palette.
- Reuse and extend the existing CSS variables for application and map roles, including backgrounds, translucent surfaces, panels, dialogs, tooltips, native controls, labels, objects/halos, grid, Jump Routes, Orbit lines, borders, hover, selection, focus, validation, and save/error states. Replace literal dark-only surfaces as necessary. No elaborate theme engine or new renderer is authorized; [Nuxt UI adoption](07-nuxt-ui-adoption.md) remains undecided.
- Theme switching changes presentation only. Preserve workspace data/placement, active map/context/tool, valid selection, temporary per-view viewport, session draft identity/content/validation, reopening paths, and save/error state. Do not remount destructively, apply/discard a draft, reset a gesture, or trigger a workspace mutation/save merely to change colors. Preserve the established draft-conflict and context-transition guards.

### Clean SVG/PNG and print palette

- Both formats default to the active UI palette and offer **Light for printing** for that export only. This option never changes the active UI or its remembered preference and does not become a separate theme engine. Resolve the requested palette on the export scene, independent of the displayed editor.
- Export the latest validated, applied in-memory map, including when its durable save is pending or failed. Include the full scene regardless of pan/zoom, with the current applied system name in a readable, non-overlapping title band whose bounds fit it. Preserve the existing distinction between system-title exports and Jump Cluster exports.
- Remove temporary selection/focus/hover emphasis, edit handles, unapplied drafts, and gesture/candidate previews from the export, including their effect on output bounds. Keep meaningful map information such as objects, labels, Orbit paths, Jump Routes, and unresolved-route cues. The displayed scene, selection, viewport, tool, gesture, draft, theme, and save/error state stay intact; exporting neither applies nor discards work.
- SVG and PNG share scene content, arrangement, palette, title, and full-scene bounds; PNG rasterizes that same export scene. A standalone SVG must be readable without the application's CSS. Export failure must leave editing state intact and explain the failed export separately from validation or durable saving.
- This is the existing Warden-facing map image export. It introduces no player/secrecy filter or data-exposure guarantee; [Player view and secret-free export](https://github.com/Submoon/ttrpg-cluster-control/issues/9) remains separate.

### States and footer coordination

- Remove the decorative footer. Relocate its useful feedback to a compact, continuously accessible status surface: draft plus reopening, Saving / Saved on this device / Not saved, and persistent save error with Retry / Export current JSON. Preserve those distinctions and actions from the state contract; an image export is not a replacement for current-JSON recovery.
- Convey important states through text, identifiable marks/shapes, line patterns, or other visible cues in addition to color, with programmatic names/states where relevant. Selection and keyboard focus must remain distinguishable even when both affect one entity. Preserve meaningful unknown-route cues and accessible icon labels/help across pointer, keyboard, and touch. [W3C use of color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html).
- The prototype chooses exact status placement, colors, shape/line treatments, typography, and dimensions, while retaining visible/reachable feedback in narrow viewports and overlays without obstructing required controls or focus. [Accessibility contrast and remove unnecessary footer](https://github.com/Submoon/ttrpg-cluster-control/issues/23) still owns the coordinated realization, contrast report, icon checks, color-blindness simulation, and no-readability-regression evidence; none is waived or claimed complete here.

### Measurable acceptance evidence for later validation

- Target at least **4.5:1 for useful text** in UI, both maps, tooltips/dialogs, draft/save/error feedback, labels, and export titles. This project target retains 4.5:1 for large useful text as well, although WCAG permits a lower ratio for qualifying large text. Measure against the actual background, including composited translucent surfaces. [W3C text contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).
- Require at least **3:1 for meaningful icons, control boundaries/state cues, and graphical parts needed to understand/use the map**, against their adjacent colors. Separate purely decorative grid lines from meaningful alignment or interaction guides; a guide needed to use the editor is not decorative. Check relevant foreground/background combinations without rounding a failing ratio upward. [W3C non-text contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html).
- Verify keyboard focus remains visible while focused and is not entirely obscured by application-created panels/status/overlays. Check selection and focus together, with cues beyond hue. Exact focus dimensions are not chosen by this ticket. [W3C visible focus](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html), [focus not obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html).
- Later evidence must cover light and dark UI, both maps, panels/dialogs/tooltips, hover/focus/selection, invalid-target/draft/save/error feedback, and readable compact icons with their keyboard/touch alternatives. Record measured color pairs, relevant states and backgrounds, and color-blindness simulation findings in the separate audit report.
- Verify each map in **active-light, active-dark, and light-print**, in both SVG and PNG, using an independent reader. Compare content, geometry, complete bounds, applied system title, label/line contrast, and absence of dark-only surfaces or temporary editor emphasis. Include dense maps, long system names, off-viewport content, a selection plus draft, an active gesture, and a failed save. Confirm export leaves the live state intact and excludes unapplied work.
- Validate first OS-derived display, explicit choice/reload/browser-session persistence, OS changes before/after explicit choice, workspace switching/import, theme switching with resumed drafts/selection/view, and export-only print choice. Contrast thresholds, screenshots, state-preservation scenarios, and independent export checks are required future evidence; no ratio, test result, browser behavior validation, or WCAG conformance is claimed by this planning session.
