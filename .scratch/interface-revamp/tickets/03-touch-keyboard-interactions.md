## Parent map

[Revamp the interface: make the map central on desktop and mobile](../map.md)

## Question

What shared interaction contract allows users to select, navigate, add/place, move, and manipulate Orbits without confusing navigation gestures with mutations on phones, desktop, and keyboard? Should the UI use an active tool, direct gestures, or an explicit combination?

## Factual context

[Revamp the interface](https://github.com/Submoon/ttrpg-cluster-control/issues/3), reviewed on 2026-10-13, makes touch support mandatory and requests evaluating a tool-based approach. The catalog uses activation plus HTML drag (`ObjectPalette.vue:21`, `:116`); the D3 canvas supports drag and pinch (`system-map-renderer.ts:559`, `:841`). Handles measure 7 SVG units and follow zoom. The narrow test suite does not use a configured touch device. See [the analysis](../analysis.md), preservation matrix and touch section.

Coordinate without implementing [Multiple selection and groups](https://github.com/Submoon/ttrpg-cluster-control/issues/6), [Orbit locking with relative position preservation](https://github.com/Submoon/ttrpg-cluster-control/issues/10), and [Annotations and schematic zones](https://github.com/Submoon/ttrpg-cluster-control/issues/11). Their future box selection/tools must not make pan impossible.

## Proposal to discuss

The initial proposal was to select a placement tool, then tap/click the map, with visible cancel/Escape, separate navigation/editing intents, optional desktop accelerators, and touch/focus alternatives to hover or right-click. The human-confirmed contract is recorded in `## Resolution` below.

## Resolution criteria

- Define tap/click intent, pan, object/Orbit drag, pinch and wheel, placement inside an Orbit or in empty space, cancel/interruption.
- Specify keyboard access and alternatives to desktop modifiers.
- Distinguish UI command state, selection, and map data; define effects of changing tools.
- List fine-grained gestures to demonstrate in the prototype and future interactions reserved for separate efforts.

## Blocked by

None: the contract for existing intents can be discussed across the two current map levels without deciding the future renderer. Apply `grilling` and `domain-modeling`. Any precise layout waits for the prototype and navigation decision.

## Resolution

Resolved on 2026-10-13 by the explicit human answers to Q1–Q9. This is the interaction contract for the revamp, not product implementation or closure of its GitHub source.

### Navigation and explicit editing

- **Navigation is the default tool.** Click/tap selects a system object, Orbit, or Jump Route; a star system opens directly under the [resolved navigation contract](01-map-navigation-boundary.md). Dragging pans the view and cannot mutate map data. Editing requires an explicitly activated tool or edit command.
- **Tool state is visible.** Provide a Return to Navigation control usable by touch and keyboard, with Escape as an equivalent shortcut. A successful Add returns to Navigation; Move/Modify remains active until explicitly exited or an accepted map-context change occurs. Invalid targeting does not exit the tool.
- **Active edit intent takes precedence.** An Add target interaction does not also select/open the target. In Move/Modify, click/tap selects a system for editing rather than opening it. Return to Navigation restores direct system activation; this explicit edit boundary preserves the earlier navigation decision.

### Placement and manipulation

| Intent | Confirmed behavior |
| --- | --- |
| Add a system-map catalogue object | Choose its subtype, then click/tap empty space for free placement or an Orbit for attached placement at the indicated position. Indicate the intended target before validation. |
| Add an Orbit | Target an object to use it as host, or empty space for an unoccupied center. |
| Move/Modify an object or system | Drag the target to edit its position; drag the background to pan. Click/tap remains target selection in this tool. |
| Modify a selected Orbit | Show controls for unoccupied-center movement, independent axis adjustment, and rotation. Dragging its ring resizes uniformly. A hosted Orbit requires explicit Detach before its center can move independently. |
| Move an attached object | A drag into empty space changes its position on its existing Orbit without detaching it. Explicitly targeting another valid Orbit transfers it. A free object may join a valid Orbit. Attached-to-free placement is an explicit action. |
| Attach an unoccupied Orbit | Moving its center onto an announced valid object host may attach it. Preserve existing host/geometry validity rules and dependent elements. |
| Resolve an ambiguous target | Require an explicit choice among valid candidates before committing. Target indication and candidate choice work by touch and keyboard, without hover. |
| Reject an invalid target | Explain the rejection, change no map data, and keep the tool active. |

Preserve existing applicable creation, hierarchy, inspector, route, and Orbit operations from [the preservation matrix](../analysis.md). The gesture contract does not remove their available commands or bypass domain validation. In particular, retain the baseline's Orbit host-minimum adjustment and its independent notice; do not silently reinterpret an invalid target as a different mutation.

### Gesture precedence and cancellation

- Two-finger pan/zoom navigates in every tool, including over map entities. When a second map contact arrives during an edit gesture, cancel its uncommitted preview before navigation begins. Pinch does not modify map data and retains the active tool.
- Normal release commits a valid gesture edit. Return to Navigation, Escape, or gesture interruption cancels the current uncommitted action. Cancelled/interrupted previews must never be committed.
- Cancellation preserves already committed edits and inspector drafts; it is not undo. A touch user has an explicit cancellation path. The exact touch control arrangement must be demonstrated in the prototype.
- Wheel input zooms the view. Rotation has dedicated controls and keyboard alternatives; no operation requires Ctrl+wheel or another modifier. Optional accelerators must conform to the confirmed navigation/edit boundary and cancellation rules.

### Keyboard and single-pointer alternatives

- Every placement/manipulation result has a path usable by keyboard and by a single pointer without dragging. Use the hierarchy to choose a target; provide Add/Place with a destination, coordinates, or Orbit and position as applicable.
- A destination command supports selecting the source and then tapping/clicking the destination, with an indicated preview and explicit Confirm/Cancel. Provide values or dedicated controls for Orbit center, axes, and rotation and applicable object/system positions. These alternatives preserve attachment and target-validity rules.
- Provide zoom in/out, Fit, and view-movement controls so navigation does not require pinch, wheel, or dragging. Enter/Space activates a focused target or control; focused arrow adjustments remain available for the corresponding settings.
- Controls have accessible names and visible focus, selection, and active-tool states. Compact icons have touch/focus access to their meaning. No operation depends exclusively on hover, right-click, a modifier, or a multi-touch gesture.
- Detailed key bindings, step sizes, hit areas, and the visual distribution of these controls are prototype/specification details, not additional choices made in this ticket.

### Context, drafts, and future coordination

- An accepted effective transition between map contexts resets the tool to Navigation. Restore viewport and valid selection according to [Set the revamp's navigation boundary against future semantic zoom](01-map-navigation-boundary.md); edit tools are not restored with view memory. If the existing draft guard refuses the transition, retain the context and its tool.
- Tool intent, entity selection, temporary gesture previews, committed map data, and inspector drafts remain distinct. This ticket defines gesture cancellation and context reset; [Define revamp guarantees for drafts, selection, and saving](05-editor-state-and-preservation.md) retains authority over concurrent inspector/map edits, draft conflicts, and durable-save/error policy. Do not infer a new conflict or autosave policy from tool activation.
- Future multi-selection/groups, Orbit locking, annotations/zones, unified navigation, and undo/redo remain separate efforts. Their tools must coordinate with safe Navigation, explicit edit activation, candidate choice, cancellation, and the direct-system-opening exception; this ticket implements none of those features.

### Required prototype demonstrations and limits

Demonstrate Navigation versus Move/Modify over both map levels; targeted Add in empty space/on an Orbit/on a host; one-shot versus persistent tool state; object transfer and explicit detachment; all Orbit controls; ambiguous/invalid candidates; second-contact takeover; touch cancellation and interruption without mutation; keyboard and single-pointer alternatives; and accepted/refused context transitions with view restoration. Include dense maps and touch/focus access rather than relying on hover examples.

No new domain term or ADR was required. No source code, dependencies, prototype, tests, branches, commits, or GitHub content were changed. The prototype ticket remains blocked by its unresolved draft/state, theme/accessibility/export, and Nuxt UI adoption decisions. Exact appearance and measurable usability criteria remain for those later stages.
