## Question

Should the project keep its current Vue/CSS components, adopt Nuxt UI selectively for overlays and controls, or adopt it more broadly? Which components and validation conditions define the choice without replacing the domain or D3/SVG rendering?

## Factual context

[Revamp the interface](https://github.com/Submoon/ttrpg-cluster-control/issues/3), reviewed on 2026-10-13, asks to evaluate Nuxt UI. [Nuxt UI: compatibility and options for the revamp](../research/nuxt-ui-fit.md) establishes compatibility across the Nuxt/Tailwind generations and compares options and risks. Its research is closed; the human-confirmed direction and conditional commitment are recorded in the Resolution below. The library does not resolve the SVG palette or print export. Modal/Slideover make the map inert by default when modal; Drawer is a different primitive, and actual weight is unmeasured. A module managing Tailwind requires coordination with the current manual Vite plugin.

## Initial proposal

The initial recommendation was selective use for dialogs, menus, tooltips, and panels. The human instead chose broad use for the prototype, with conditional final adoption and documented exceptions. The Resolution supersedes this initial proposal.

## Resolution

Resolved on 2026-10-13 through explicit human answers **Q1 B, Q2 A, Q3 A**. This authorizes a broad Nuxt UI direction for a disposable prototype and defines its evaluation boundary; it is not unconditional adoption for the production refactor. The next prototype can proceed without waiting for final adoption. [Confirm Nuxt UI adoption from prototype evidence](08-confirm-nuxt-ui-adoption.md) will make that subsequent human decision from actual results.

### Scope and responsibility

- Use Nuxt UI broadly in the prototype for buttons, fields, forms, panel envelopes, dialogs, menus, help, and compact controls. Exact primitives, layouts, dimensions, and styling are prototype choices. The rationale is to evaluate the consistency and maintenance value of a common interface foundation across realistic editor flows, rather than restrict the trial to a few overlays.
- Keep separate Jump Cluster and star system maps, existing D3/SVG ownership, geometry, domain commands/validation, persistence, and JSON/image interchange boundaries. A generic library form validator may present feedback; it does not replace authoritative domain validation or publish/save workspace data by itself.
- Preserve the authoritative [navigation](01-map-navigation-boundary.md), [interaction](03-touch-keyboard-interactions.md), [draft/save](05-editor-state-and-preservation.md), and [theme/export](06-themes-accessibility-export.md) contracts. They govern the integration, regardless of library defaults.

### Adaptation and targeted exceptions

- Adapt a Nuxt UI primitive first when it fits the required behavior. If it cannot preserve a mandatory editor contract adequately, or adaptation is less suitable than a specific application container/component, document the exception's surface, rationale, retained Nuxt UI controls, and validation evidence. Exceptions must remain targeted; they are not blanket custom-interface adoption or nominal wrappers without library value.
- Map-editing panels must permit independent map pan/zoom while a draft is active. Use persistent/non-modal presentation for those panels; a default modal drawer/slideover that makes the map inert cannot silently replace this behavior. Genuine modal confirmation flows retain appropriate focus containment and return. Demonstrate focus, dismissal, touch scrolling, keyboard access, and map gestures rather than inferring them from the primitive's name.
- Own draft identity/content/validation, selection, context/tool/view, and save/error state outside library mounting. Hide/reopen, responsive reflow, tool/theme changes, and presentation remounts preserve session drafts. Library close events cannot implicitly discard them. Maintain targeted conflict exclusion, Apply/Discard/Stay guards, and accurate lossless previews. Validated in-memory publication ends Apply's form; ordered durable saving and persistent error/Retry/current-JSON-export remain separate, without replaying creations. Cancellation is not undo.

### Integration and acceptance gates

- Retain an SSR interface shell with existing `ClientOnly` D3 maps. Validate first render, hydration, overlay/portal focus, initial OS-derived theme and remembered preference on reload; do not wrap the entire page client-only merely to integrate the library. Coordinate the module/provider/CSS integration with the existing Tailwind registration to avoid duplication; verify global field/focus styling in the combined interface.
- Bridge Nuxt UI and both maps through the agreed CSS-token palettes. Preserve local browser/device theme preference, compact accessible draft/save/error status, and clean applied SVG/PNG with the independent light-print option. Theme switching/export cannot mutate data, destroy drafts, or recolor the live editor solely for export. Exact palette values and the separate measured accessibility audit remain later work.
- Collect representative desktop and modest-mobile evidence using dense maps and real form content, portrait/landscape/short viewports and virtual keyboard, touch/keyboard/single-pointer paths, nested overlays, scroll/focus restoration, drafts, selection/view restoration, validation refusal and durable-save failure. Exercise both map levels and light/dark presentation rather than only static empty-screen mockups.
- Verify actual offline resource behavior for selected/dynamic icons, fonts, and other runtime requests; a library default does not establish local-first availability. Compare equivalent current-interface and broad-prototype production builds/scenarios: transferred initial/deferred JavaScript, CSS and resources, startup/mount, overlay interaction, and map pan/zoom. Record versions, data, device/browser, method, results, and limits. No universal bundle figure, numeric performance budget, installation success, or accessibility conformance is asserted here.
- Final adoption requires the human to judge actual benefit and measured costs alongside demonstrated mandatory behavior, and to confirm or revise scope/exceptions in the follow-up decision. Missing evidence remains explicit and cannot be treated as a passed gate. If the prototype exposes an additional technical question, state a precise investigation/artifact rather than turn a static mock into a performance claim.
