# Browser measurement methods: source definitions and limits

Checked 2026-10-14 against official sources. Experiment baseline: `629d2a98715c3a16b954e0f77c639b1f0c31212c`; the parent investigation confirmed `HEAD == origin/main` after fetching. This note supplies measurement caveats, without an adoption verdict.

## Network metrics

- `Network.requestWillBeSent` announces an impending HTTP request and carries request ID, URL, resource type, timestamps, and optional redirect response. `loadingFinished` means the HTTP request finished; its `encodedDataLength` is the total bytes **received** for that request. It is not uploaded request bytes, and the definition does not make it a body-only measurement. Keep the name **CDP received bytes**, record the collection interval and resource filters, and retain failed requests separately; they emit `loadingFailed`. Redirects need explicit accounting. The newer experimental `encodedBodyLength` explicitly excludes headers and transfer framing. [CDP Network source](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Network.pdl)
- Resource Timing `encodedBodySize` represents the response body before content decoding. `transferSize` is a distinct metric: the current W3C draft returns encoded size plus a fixed 300-byte allowance, zero for local cache, or 300 for validated cache. It therefore cannot certify exact wire/header bytes. Cross-origin exposure restrictions can zero size fields; service-worker results can conceal internal fetches. Entries are bounded by a resource-timing buffer. Record cache/service-worker policy and distinguish navigation entries from resource entries. [Resource Timing specification](https://www.w3.org/TR/resource-timing/#dom-performanceresourcetiming-transfersize)

## Emulation and execution

- `Emulation.setCPUThrottlingRate` takes a slowdown factor: `1` is unthrottled; `4` means fourfold slowdown. Chrome documents that this is relative to the host computer and that mobile CPU architecture is not reproduced. Thus use **host CPU at 4x slowdown**, not a physical-phone performance claim. These CPU/network/viewport settings do not establish matched phone GPU or memory hardware; this is a limitation inferred from the documented emulation scope. [CDP Emulation source](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Emulation.pdl), [Chrome device-mode limitations](https://developer.chrome.com/docs/devtools/device-mode#limitations)
- `Network.emulateNetworkConditions` defines minimum request-to-response-headers latency in milliseconds and aggregated throughput in **bytes/second**, with `-1` disabling throughput throttling. It is deprecated in current protocol documentation in favor of rule-based conditions plus navigator-state override. A localhost server with synthetic latency remains a controlled local experiment; it does not measure deployed server, DNS, TLS, or Internet-path behavior. [CDP Network source](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Network.pdl)
- Playwright device descriptors emulate browser parameters such as viewport, user agent, scale, and touch. Record exact binary/version, channel, and headed/headless setting: default Chromium headless shell differs from regular headed Chromium; branded Chrome/new headless uses another execution mode. Hold these constant across comparisons. [Playwright emulation](https://playwright.dev/docs/emulation), [Playwright browser modes](https://playwright.dev/docs/browsers#chromium-headless-shell)

Exact wire-byte, body-byte, production-latency, or physical-phone claims would exceed these measurements. Controlled comparative results remain useful within their recorded conditions.
