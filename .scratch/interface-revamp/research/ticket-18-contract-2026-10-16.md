## Data and recovery invariants

- Keep IndexedDB database `ttrpg-cluster-control`, database version 1, object store `workspace`, records `current` and `last-valid`; preserve map marker `ttrpg-cluster-control-map`, schema/version and supported older shapes inside that boundary. No migration, older-marker fallback, alternate database, sample hydration or durable drafts.
- Loading has a truthful status and no editable creation form or map. A missing `current` yields the ready creation form. An invalid or unavailable `current` yields actionable load error, Try again and Restore last valid backup; it never yields a partial editor or automatic replacement.
- New creation uses `createLocalWorkspace` through existing `submitNames`/`commit`; tests use names unique to the case, observe Saving/Saved and reload the actual durable result. Validation runs before publication. Normal commits publish a validated detached snapshot in memory before their queued durable write; this established distinction must not be conflated with restore.
- Try again calls `hydrate`, clears previous load/recovery feedback for the new attempt, re-reads current storage and resumes only a validated record. It is load retry, not the future latest-applied-save Retry from ticket 20.
- Restore validates `last-valid` and writes it to `current` in one read-write transaction. `restoreWorkspaceBackup` resolves only after transaction completion; only then may `useLocalWorkspace.restoreBackup` publish the editor. The backup remains intact. Missing/damaged backup or aborted replacement leaves `current` unchanged, workspace unavailable and clear recovery feedback. A later successful retry/restore must remain possible.
- Keep error messages in text/alert semantics and state cues beyond color. Do not change ordinary save failure/session-ending behavior to implement future tickets 20 or 21.
