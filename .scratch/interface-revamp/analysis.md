## Factual synthesis

1. A “map-first” interface already exists, with a full-area SVG scene and absolutely positioned panels. The desired improvement is not just a wider SVG: reduce the area actually obscured, clarify controls, and establish safe touch gestures.
2. The domain and persistence are already separate from the Vue shell. A redesign can preserve commands and the data format. A unified map, however, would change coordinate spaces, renderer mounting, and the navigation contract; its separate effort needs an explicit boundary.
3. The current model has a single selection, two distinct views, inspector-local drafts, and renderer-local geometric previews. There is no persistent tool command, undo/redo stack, or multi-selection model.
4. Merged Orbit host-minimum and snapshot-recovery corrections are preservation requirements. Remaining competing-draft and creation-default risks are observable statically; they should inform the new UI's guarantees and be reproduced/handled in separate reliability issues.
5. Map colors mostly use CSS variables, but the shell retains several literal dark backgrounds. Export freezes computed styles from the active scene; a light export independent of the UI requires an explicit contract.
6. Test definitions cover flows, exports, narrow viewport sizes, and snapshot recovery. No suite was executed in this analysis; this review does not establish successful touch gestures, two themes, or WCAG conformance.

## Touch, pointer, and responsive layout

**Observations.** `assets/css/map-workspace.css:459`–`:527` sets the editor to flex with an absolute map at `inset: 0`, and overlays palettes/panels. `MapEditorLayout.vue:134` positions panels at fixed `top` values (10rem, 18.25rem for system); its code at `:97` detects ≤760px and prevents two panels from being open together. Breakpoints at 1100/1200/760/360 and very short landscape layouts exist (`map-workspace.css:684` onward). Tests in `workspace-ui.spec.ts:12` compare SVG width with viewport dimensions at 1440×960 and 390×844, and check for no overflow and alternating panels. They do not measure how much of the map remains unobscured when a palette/panel stays open.

The D3 zoom filter excludes marks and allows wheel and multi-touch pinch (`ClusterMap.vue:311`, `system-map-renderer.ts:841`). Objects use D3 drag; the catalog uses HTML drag and `DataTransfer` (`ObjectPalette.vue:106`). Click/keyboard activation is already an alternative, but chooses a default position or the selected Orbit; it does not place by touch at a chosen point. Orbit handles are drawn at a radius of 7 scene units (`system-map-renderer.ts:285`, `:309`), and rings have a 16-unit hit area (`SystemMap.vue:268`). These dimensions scale with SVG zoom; they are not fixed-size screen targets.

**Proposals to discuss.** A visible active tool, choose a type then tap to place, explicit cancel/Escape, a navigation mode distinct from editing gestures, and common command access through buttons/toolbars. Avoid commands available only on hover, right-click, Shift, or Ctrl; these interactions can remain desktop accelerators. Icon tooltips need a touch and focus alternative. The hierarchy/details could become temporary panels or a mobile sheet based on the prototype; this choice is unresolved. Include the virtual keyboard, safe areas, portrait/landscape, and resizing in the evaluation.

**Unknowns.** One-finger or two-finger pan, behavior when a drag starts on an object, priority of a pinch started on a handle, threshold between tap/drag, handling of `pointercancel`/touch interruption, effective touch target size at minimum zoom, preserving map center after opening a panel, keyboard movement method for objects/systems, tablet/stylus, representative map sizes. None of these choices follows automatically from D3 recognizing touch events.

## UI state, map commands, and reliability

Separating five states helps prevent a panel, tool, or theme change from accidentally modifying data:

| State | Current owner | Current durability | Contract pointer or remaining UI question |
| --- | --- | --- | --- |
| Committed data and layout | `useLocalWorkspace` + domain functions | IndexedDB/JSON | [Resolved application/save contract](tickets/05-editor-state-and-preservation.md) |
| Pan/zoom and gesture preview | D3 renderer, maps | Transient, omitted from JSON | [Resolved navigation](tickets/01-map-navigation-boundary.md) and [gesture contract](tickets/03-touch-keyboard-interactions.md); visual realization awaits the prototype |
| Selection/context | Unique IDs in `useEditorState` | Transient | [Resolved preservation/transition contract](tickets/05-editor-state-and-preservation.md); panel arrangement awaits the prototype |
| Form draft | Inspectors, chart names, and field-definition dialog | Transient until application | [Resolved draft authority and lifetime](tickets/05-editor-state-and-preservation.md) |
| Active UI command | Today mostly panel/catalog family/menu | Transient; no tool model | [Resolved tool contract](tickets/03-touch-keyboard-interactions.md); placement of controls awaits the prototype |

The single persistence owner is a documented architectural invariant (`pages/index.vue:230`, `useLocalWorkspace.ts:26`). `commit` first creates a detached, validated snapshot, then publishes memory **before** its durable write, with a write queue and status revision (`useLocalWorkspace.ts:65`). Validation failure does not publish the candidate. A durable-write failure retains the valid in-memory snapshot and the error; “Save failed” therefore does not mean a full return to the old workspace. Backup restoration instead publishes only after its durable replacement succeeds. The new UI must distinguish validation, persistence, recovery, import, and export failures. The footer currently carries detailed save feedback (`pages/index.vue:212`), so removing it requires relocating that information.

`confirmDiscardInspectorEdits` checks inspectors and `chartNamesEditing`, then calls `window.confirm` (`useEditorState.ts:177`). Navigation/selection/import goes through this guard; collapsing panels does not. Inspector components use `v-if` (`MapInspector.vue:51`): unmounting them changes where drafts live. A new conditional UI could therefore lose drafts simply by changing its presentation if it does not define a stable owner.

**Orbit draft versus map.** Draft radii are not resynchronized during editing (`OrbitInspector.vue:282`). The intent to simplify the editing entry point is clear, but blindly removing Chart Details would lose summaries and navigation back to the chart context. Have the human decision distinguish map title from object name.

## Themes, accessibility, and exports

`assets/css/main.css:3` sets `color-scheme: dark` and defines UI and map tokens. No light/dark control or user preference was found. Maps use `--map-*` tokens; overlay backgrounds remain literal, including at `MapEditorLayout.vue:143`, `ClusterMap.vue:360`, `ObjectPalette.vue:140`, and `map-workspace.css:370`, `:404`, `:620`. Tokens must also cover transparency, shadows, borders, halo, accent, focus, error, and dialog surfaces; changing only `--app-bg` would be insufficient.

`createExportSvg` clones the scene and inlines computed styles (`map-image-export.ts:92`), removes the viewport transform and `.orbit-edit-control` (`:90`, `:104`), fits surfaces to the full content (`:120`), and adds a system title. Selected/focus classes are not explicitly removed here: the exported palette follows the rendered state at export time. The human-confirmed export policy is now authoritative in [Define the light/dark, accessibility, and export palette contract](tickets/06-themes-accessibility-export.md); it remains to be implemented. PNG uses this same SVG, so both formats must satisfy that contract without changing the live editor.

WCAG requirements of 4.5:1 for text and 3:1 for components come from [Accessibility contrast and remove unnecessary footer](https://github.com/Submoon/ttrpg-cluster-control/issues/23). No ratio was calculated and no conformance is claimed in this audit. Light/dark themes and distinguishable states are already source requirements, even though the formal/color-blindness audit is coordinated separately. Marks exist as glyphs (`utils/catalogue-marks.ts`); compact icons must remain identifiable on focus/touch. Color alone is insufficient for save/error, selection, hidden objects, or future secret information. Retain ARIA names, keyboard commands, visible focus, dialog focus reset, and reduced motion.

## Architecture and seams to preserve or clarify

Nuxt SSR serves the shell, IndexedDB loads after mount, and maps live in `ClientOnly`; Vue handles controls/lifecycle and D3 handles SVG subtrees (`SystemMap.vue:23`). `domain/workspace.ts` is a stable facade over domain modules (modularization described by V1 ticket 29); geometry utilities separate placement and drawing; workflows translate UI events into domain functions and `commit`. `package.json` does not include Nuxt UI or Pinia; declared dependencies Nuxt `^4.6.0`, Tailwind `^4.3.3`, D3 `^7.9.0`, tests `^1.64.0` do not prove the exact installed versions.

Favorable seams: shell/layout around hierarchy/map/inspector slots; `WorkspaceHeader` dispatching file actions; `ObjectPalette` catalog intents; inspector contracts for save acknowledgement and draft guard; map components exposing export; `useWorkspaceFiles` as the single import/export boundary; `commit` as the single mutation boundary. Reusing these boundaries enables a redesign without a new domain engine.

Seams to implement under the [resolved interaction contract](tickets/03-touch-keyboard-interactions.md) and [resolved preservation contract](tickets/05-editor-state-and-preservation.md): shared tool state, gesture transaction, and draft ownership independent of visual mounting. Remaining design concerns include future multi-selection without arbitrarily changing every command, UI/export palette projection independent of data, and navigation to future modules without speculative generic entities. The cluster map remains monolithic in `ClusterMap.vue`, while the system has a dedicated renderer; that alone does not justify premature unification.

Preserve the existing command/rendering seams rather than introducing a second renderer, force simulation, Pinia, or remote service without a demonstrated concrete need. Research in [Evaluate Nuxt UI for the revamp without destabilizing map rendering](tickets/02-nuxt-ui-fit.md) is closed, with the report [Nuxt UI: compatibility and options for the revamp](research/nuxt-ui-fit.md). It establishes generation compatibility and potential value without measuring actual weight or validating behavior in the application. ## Risks and decision criteria

| Risk | Consequence | Proposed mitigation / required evidence |
| --- | --- | --- |
| New shell unmounts inspectors | Draft lost on close/theme change | Stable owner and a theme/panel/context scenario with a draft |
| Competing pan/edit/pinch gestures | Unintended change that cannot be undone | Mode contract + coarse-pointer prototype, explicit cancel |
| Compact palette available only on hover | Feature unavailable to touch or keyboard | Accessible name and tap/focus alternative, evidence on a small screen |
| Large SVG hidden by overlay | Map is dominant only geometrically | Criterion for area that is actually usable and virtual-keyboard scenario |
| Export captures accidental palette/selection | Illegible labels or unexpected rendering | Two-palette export policy, compare full-scene SVG/PNG |
| Unfixed competing-draft behavior for [Orbit draft in inspector overrides map edits](https://github.com/Submoon/ttrpg-cluster-control/issues/16) | Overwritten edits attributed to the revamp | Dedicated diagnostics and [resolved preservation/integration requirements](tickets/05-editor-state-and-preservation.md); do not claim a fix |
| [Unified map with semantic zoom](https://github.com/Submoon/ttrpg-cluster-control/issues/4) merged into the revamp | Renderer rewrite and scope drift | Navigation/unification decision as prior coordination |
| Coordinated campaign issues become automatic scope | Effort much larger than its destination | Limit future surfaces and contracts; implement separately |

## Recommended boundary for human decisions

Navigation, interactions, state preservation, and theme/export policy are resolved through the human exchanges in [Set the revamp's navigation boundary against future semantic zoom](tickets/01-map-navigation-boundary.md), [Decide touch, mouse, and keyboard map gestures and controls](tickets/03-touch-keyboard-interactions.md), [Define revamp guarantees for drafts, selection, and saving](tickets/05-editor-state-and-preservation.md), and [Define the light/dark, accessibility, and export palette contract](tickets/06-themes-accessibility-export.md). Those tickets are the authoritative locations for their contracts, including measurable contrast/focus targets and separate audit coordination. [Decide Nuxt UI adoption and scope](tickets/07-nuxt-ui-adoption.md) is also resolved: the [prototype](tickets/04-map-first-ui-direction.md) is open and unclaimed. It should demonstrate broad Nuxt UI use and existing operations with real content, human reactions, and representative integration measurements. [Final adoption confirmation](tickets/08-confirm-nuxt-ui-adoption.md) is blocked by that prototype, without a dependency in the opposite direction.

For drafts, touch, and themes, apply the authoritative resolved contracts above rather than reopening their strategy choices; use the prototype to evaluate their presentation, exact palette values, and status placement. The separate accessibility report still requires measured evidence; no conformance is established by these planning decisions.

## Sequence toward a specification, without implementation breakdown

1. Use the resolved navigation, interaction, preservation, theme/export, and broad Nuxt UI prototype-direction contracts.
2. Prototype UI directions with real content and interactions: dense map, catalog, selection/draft, save error, route draft, touch placement, and virtual keyboard. Collect human reactions and the adoption contract's representative measurements; this remains disposable work, not product delivery.
3. Confirm or revise final Nuxt UI adoption from the actual evidence in its follow-up decision; formulate fine-grained visual decisions still in the fog, such as area occupancy, visible commands, exact panel/focus presentation, labels, hit-target scale, and re-entrant states. Add specific tickets only when the question can be stated without presupposing an answer.
4. Produce a behavior specification and preservation criteria using the synchronized baseline, coordinating separate reliability fixes and preserving the implemented product identity. Create implementation tickets only after the destination is reached and corresponding authorization is given.

The current test suite is available evidence of historical contracts, not a design to copy. Some tests enforce the current dark color or panels; future validation should preserve operations/data while replacing presentation assertions that have become obsolete. Later, add scenarios for touch and keyboard, two palettes/reload, drafts/panel/theme, load/save errors, cascades/import cancel, and full export in two themes. No suite results are reported here.
