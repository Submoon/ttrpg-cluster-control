# Retrospective: test value and development feedback cost

## Findings for the user

The concern about time spent waiting for and repairing tests is supported by the selected sessions. Several complete local selections took 30–84 minutes, and small product changes triggered long browser qualification plus unrelated preparation repairs. The evidence does not establish that most active development time is testing: tool calls overlap, agents work while runners execute, and some long turns include substantial new requirements and UI reconstruction.

The count alone does not establish excessive coverage. The pre-integration quality branch has 472 cases, including 190 pure cases and one storage case; 281 belong to the browser project. After main reconciliation, coordinator discovery reports **581 cases in 94 files: 265 pure, 315 browser and one storage**, with no duplicate project/file/title selections. This is discovery, not execution success. The increase of 109 cases (+75 pure, +34 browser) comes from incoming Search and verification tooling, not a new ticket-09 coverage matrix. Completed consolidation removed just one net browser case in ticket 07 and reduced repeated workflows rather than radically changing the allocation. There is still a useful, bounded next pass: remove incidental presentation obligations, consolidate deterministic permutations at their existing lower boundaries, and shorten ordinary feedback while retaining representative real browser interactions.

Recurring timeouts are an unresolved reliability and feedback-cost problem. They should not become routine accepted noise. Four of the five selected completed chats contain native deadline failures, as do the supplementary quality batches. The last pre-integration complete run had nine deadline failures among 281 browser cases (about 3.2% in that one run), plus a distinct pre-deadline Undo assertion failure. That is an observed run outcome, not a statistical flake rate. Fixing the ownership and cause of each class is more useful than repeatedly rerunning or increasing all timeouts.

Behavior should be the default acceptance criterion. Exact footer widths, alignment, a particular outline style and framework popover states are weaker long-term contracts than successful editing, focus ownership, unobstructed actions, visible names and durable map changes. Cartographic geometry, clipping that prevents use, keyboard focus, contrast and hit testing remain useful browser behavior. The recommendations below distinguish these cases instead of treating every rendered assertion as expendable.

The user's 2026-11-04 follow-up strengthens R1: permanent tests must justify an identifiable user failure. Purely aesthetic checks can be temporary implementation aids, then be removed; low-value tests can be deleted without replacement. The execution plan is three sequential sub-agent passes with increasingly demanding retention criteria, ending with Astra at High reasoning. The [R1 execution plan](#r1-extension-three-increasingly-selective-pruning-passes) defines the decisions, safeguards and completion evidence; current delivery is recorded under [the follow-up plan](#prioritized-plan-and-proposed-follow-ups).

This report is an analysis deliverable for [ticket 10](tickets/10-retrospective-test-session-problems.md). No recommended product, test, CI, personal-skill or global-instruction change is implemented by this ticket.

## Existing environment: what already works

The repository has active CI guardrails: ESLint, typecheck, production build, pure/storage tests and browser qualification. This is not an un-linted or unverified repository. `npm run test:pure` is already independent of app/browser infrastructure. Narrow file/grep selections and `npm run test:local` already exist. Lint cannot decide whether an exact geometric or visual assertion is useful; it should not be asked to enforce a blanket ban on CSS, timers, `force`, numerical tolerances or browser cases.

Incoming main adds `scripts/ci/verification.mjs`, the shared `scripts/verification-inputs.mjs` policy, Markdown checks, docs/full/direct-predecessor reuse, `@preview-smoke`, and a required quality gate. Its local launcher owns browser readiness, source/HMR invalidation, ports, child processes and per-run artifacts. That automation addresses large portions of P07/P12/P15/P16. Recommending a second framework or new witness implementation would duplicate completed work. Ticket 09 must qualify the combined branch and correct any semantic merge gaps.

The launcher currently retains one source monitor and one browser-readiness probe for its entire session. Their invalidation is permanent; `runTest` rejects a recorded source/readiness failure before spawning Playwright, while pressing Enter calls the same `runTest` without rebuilding those resources. It therefore supports repetition against unchanged inputs, not an ordinary edit-and-rerun loop after a relevant idle edit. This source-confirmed gap motivates the narrow R3 extension below; it does not weaken the existing requirement to freeze inputs throughout a run.

#### Permanent coverage and temporary verification

The retention question is: **What concrete user problem could escape if this test were removed, and why is the remaining coverage insufficient?** Keep useful domain, controller, browser and tooling behavior at the narrowest existing boundary that reproduces the failure. A past failure or the mere existence of a test is evidence to inspect, not automatic justification for permanent retention.

An exception needs a named lasting requirement and a focused test.

These decisions apply to assertions and whole scenarios. Removing a few CSS assertions mainly reduces maintenance; reducing runtime requires removing unnecessary journeys, preparation, permutations and downloads as well. ### R3 extension: requalify between idle local runs

Static evidence is in [the owned launcher](../../scripts/local-test.mjs): `start` creates `sourceMonitor` and `browserReadiness`; `runTest` checks sticky `sourceFailure` / `readinessFailure`; `runInteractiveSession` invokes the same `session.runTest(args)` after Enter. [The source monitor](../../scripts/local-source-monitor.mjs) returns its prior invalidation from `check`, and [the readiness latch](../../scripts/local-browser-readiness.mjs) resolves once for the probe's lifetime. No idle rebaseline operation exists. A new local session is the current supported recovery after a relevant edit.

A supplementary current-batch observation explains why this gap deserves measurement: `test-results/tickets-09-10-control/focused-1793784730281-proof.json` records server 1 `startToReadyMs: 92305.7399`, while its server log reports Nuxt ready in 23.5 seconds. The complete readiness figure includes HTTP and hydrated-browser preflight; the two numbers describe different milestones. The log is `test-results/local-test-2026-11-04T09-32-11-330Z-42940/server.log`, with outer `focused-historical-failures.log` in the control directory. The owned session closed and its proof records port release. This is a single warm functional-preflight observation, not a matched performance comparison, proof of the gap's frequency or an estimate that requalification would save 92 seconds.

The proposed change belongs in the existing launcher and should establish a fresh verification epoch only between completed runs:

- After the test child and its cleanup have finished, let the next explicit rerun close the previous monitor/probe, capture stable current inputs and obtain fresh browser readiness on the owned live server. If inputs or HMR change during requalification, reject or restart that bounded preparation instead of accepting a mixed candidate. Runtime/configuration changes that the live server cannot safely absorb must require a fresh session.
- Keep source/HMR invalidation permanent for each active preparation/verification epoch, including edits restored before a scan and a test process that exits zero. Preserve its invalid result and artifacts; never relabel that run valid when later requalification succeeds.
- Replace epoch-owned resources and callbacks together, so an old invalidation or cancellation cannot poison or approve the next run. Retain fresh per-test browser contexts, separate per-run artifacts, bounded cancellation and server/process/port cleanup.
- Verify unchanged-input repetition, an idle edit followed by successful requalification, a relevant edit during active tests, changes during preparation, stale callbacks and cancellation/cleanup through the existing launcher test seams. Then exercise one real edit-and-rerun on the live server and compare complete costs with a fresh-session control under matched source, selection, cache and readiness conditions. A strict first-cold protocol continues to use an independent server/context with disclosed preflight conditions; this warm optimization cannot replace it.

This is a proposal only. Its benefit and implementation fit remain to be demonstrated; preserving frozen active runs is part of acceptance, not a tradeoff to remove.
